# ADR 0064 — Phase 20.15 Production Execution UI

## Status

Accepted for Phase 20.15 implementation; local validation pending.

## Context

Phases 19.6 and 20.3 through 20.9 established the governed ProductionQueue, worker/lease authority, provider execution contracts, provider registry, live ComfyUI adapter, durable execution records, monitoring/reconciliation, and Generated Media ingestion. Phase 20.14 exposed authoritative Generated Media governance to desktop operators, but VSCS still lacked an operator workspace that starts approved scheduled production and carries completed provider output into Generated Media.

The production provider writes raw files into provider-owned storage. VSCS must not treat that location as authoritative media storage. The operator also requires a predictable project media-output location, preferably configurable while retaining a safe standard default.

## Decision

### Execution workspace boundary

The desktop shell exposes a `Production Execution` workspace separate from Production Planning and Generated Media.

Production Planning remains responsible for creating ProductionTasks, assigning provider-neutral resources, persisting schedule revisions, and obtaining explicit human schedule approval. Production Execution may discover work only by compiling the current approved schedule through `ProductionQueueCompilerService`; it does not manufacture executable work from unscheduled tasks.

The presentation layer delegates commands to `ProductionExecutionUiService`. The concrete local ComfyUI composition lives behind the `ProductionExecutionBackend` protocol.

### Existing execution authority is reused

Starting production delegates to the existing Phase 20 `QueueProviderExecutionService`. That service remains responsible for provider eligibility, Phase 19 claim/start transitions, worker leases, durable execution preparation, provider submission, and reconciliation.

Phase 20.15 does not introduce a second queue, retry model, provider lifecycle, or completion authority.

The project-scoped local ComfyUI backend shares one `ProductionWorkerRegistry` and one `ProductionLeaseManager` for its lifetime. Consequently, two UI actions cannot independently acquire the same scheduled worker/resource merely because separate execution-service objects were composed. The local ComfyUI worker advertises only `VIDEO_GENERATION`; task capabilities are not copied into the worker as implicit new authority.

### Production package

The v7.1.4 ComfyUI production workflow consumes an explicit production-package JSON file. Current ProductionTask persistence contains governed package identity/provenance but not a reliable concrete filesystem path to that exact runtime JSON document. Phase 20.15 therefore requires the operator to select the production-package JSON explicitly rather than guessing, transforming, or silently substituting another planning artifact.

The selected file is injected through the existing semantic production-package workflow binding. Workflow node IDs remain non-authoritative.

### Provider composition

Phase 20.15 provides the first desktop live-execution composition for local ComfyUI video generation. The deterministic local provider registration is infrastructure configuration, not ProductionTask authority. Registrations created by this workspace are marked as managed by `production-execution-ui`; managed registrations may be refreshed from the current renderer settings. An existing registration not carrying that ownership marker is not silently overwritten.

General provider choice and multi-provider operator controls remain Phase 20.17 work.

### Provider output versus authoritative Generated Media

Provider completion alone does not create authoritative media. On a completed reconciliation the backend passes the durable execution record, matching ProductionTask, and discovered `ProviderExecutionOutput` records to the existing `GeneratedMediaIngestionService`.

The provider source file remains in the configured ComfyUI output directory. VSCS copies the bytes and verifies the copy through `LocalGeneratedMediaFileStore`; it does not move or delete the provider source.

### Project Media Output location

`WorkspaceSettings.media_output_directory` defines the VSCS-managed project media root. Its default is:

`Media Output`

Therefore a project with no custom setting stores authoritative generated bytes beneath:

`<project>/Media Output/`

The setting is always project-relative. Absolute paths, drive-qualified paths, `..` traversal, and the project directory itself are rejected. A nested project-relative value such as `Production/Final Media` is permitted.

The ComfyUI source output directory is a separate renderer setting and may be outside the project because it is provider-owned source storage.

`LocalGeneratedMediaFileStore` retains its previous behavior when no managed root is supplied, preserving Phase 20.9 compatibility. Phase 20.15 supplies the configured project media root so the authoritative `GeneratedMedia.file.relative_path` points to the managed project copy, for example:

`Media Output/generated_media/<production>/<episode>/<task>/<media-id>.mp4`

### Restart boundary

The workspace may display durable execution summaries after restart, but it does not fabricate a lost Phase 19 lease or silently resume detached provider execution. Live restart/provider reconciliation remains Phase 20.16.

## Consequences

- Operators can start approved scheduled video production from the desktop application.
- Existing queue, lease, provider, durable-execution, and ingestion authorities remain intact.
- Same-resource execution is protected by shared session lease authority.
- Completed provider files automatically become authoritative Generated Media records through the established ingestion service.
- Authoritative media bytes are copied into a deterministic project-owned location.
- `Media Output` works without configuration, while advanced users may choose another safe project-relative folder.
- Provider raw output remains provenance/source material and is not deleted by VSCS.
- The current explicit production-package selector avoids inventing a filesystem binding that the planning model does not yet persist.

## Deliberately deferred

Phase 20.15 does not implement:

- restart-time live provider reconciliation or lease reconstruction (Phase 20.16);
- general multi-provider selection or provider-management UI (Phase 20.17);
- automatic or AI provider selection;
- automatic production-package path inference where no governed path exists;
- distributed worker/resource locking across multiple VSCS processes;
- new retry or queue authority;
- Generated Media technical validation, review, approval, or selection rules already owned by Phases 20.10 through 20.14;
- media deletion/garbage collection;
- post-production/mastering controls.
