# Video Series Studio (VSCS) — User Manual

**Document status:** Living user/operator manual, **v0.1 initial foundation**  
**Last verified:** 2026-11-04  
**Audience:** VSCS operators, reviewers, authors, technical acceptance testers  
**Scope:** Actual VSCS framework workflows, not aspirational features. Screens and controls are marked **Verified**, **Code-confirmed**, **Pending UI validation**, or **Planned**. This is **not yet a complete user manual**.  
**Primary operating principles:** Automation; continuity of narrative/assets; low cost/free local generation when feasible; ease of use; explicit governance; evidence-based acceptance.

This manual lives in the VSCS repository and must change with each material UI or workflow change. The source of truth for a feature's actual behavior is the current working-branch code and a successful operator UI acceptance. Do not present a planned feature as available, and do not assume a proposed item is production authority.

## 1. Read this first: objects, authority and safe operation

VSCS contains **different kinds of records**. Confusing them creates false failures and can cause unsafe downstream generation.

| Object | Meaning | What it does NOT automatically establish |
|---|---|---|
| Story source (.txt/.docx/etc.) | Narrative supplied to Story Analysis | Analysis, approved Canon, Episode/Scene/Shot plan |
| Story metadata | Author, synopsis, genre, themes, audience, etc. | `Analysed` or `Approved` status |
| Story Analysis result | Structured analysis, entity candidates, knowledge graph and cached evidence | Human approval |
| Approved Story | Governed Story approved after analysis and metadata completion | Governed production plan or approved CAP |
| Automation proposal | AI/deterministic suggested Episode, Scene, Shot, environment, etc. | Governed planning authority |
| Reviewed proposal | Human review recorded | Compiled plan |
| Accepted proposal | Explicitly authorised for governed compilation | Creation of final production authority before compilation |
| Compiled accepted proposal | Passed into existing governed planning services | Universal readiness of every dependent asset, CAP or provider |
| Registered asset | Project asset identity and category | Approved canonical profile or image |
| CAP | Canonical asset specification / design profile; may be Draft | Canon approval or a production-ready reference |
| CAP cached proposal | Reusable, potentially provider-inferred design suggestion | Canon, current context verification (legacy cache), or approval |
| Canonical production reference | Governed asset visual reference | Generated by planning or CAP draft saving |
| Production package | Approved production execution material | Permission to run live H3 without separate readiness gates |

**Never** change `planning/*.json`, the project SQLite database, approved asset statuses or source hashes manually to pass acceptance. Use the application's governed controls or isolated automated fixtures.

### 1.1 Lifecycle guardrails

1. Story: **Draft/Imported → Analysed → Approved → optionally Locked**.
2. Automation: **Generate Proposal → Review → Accept → Compile Accepted**; inspect the compiled, governed result separately.
3. CAP: **Discover Asset → Prepare Context (Offline) → Prepare Queue (Offline) → Review Cached Proposal / explicitly generate if needed → Review attributes → Save reviewed Draft**. Reference generation and Canon approval are separate.
4. Execution: production asset readiness, Shot/package authority, provider readiness, and the H3 live-generation hold are separate checks.

Do not treat a green test fixture as proof of real-project production readiness. Record which project, Story revision, assets, statuses, reference paths and operator confirmations were actually checked.

## 3. Story definition and analysis — operator verified

### 3.1 Create or import the Story

**Story → Story Definition** (Story Workspace):
1. Select **New Story** (or **Import Story…**).
2. Enter the Story title and description.
3. Set or browse a genuine **Source path**, choosing the correct source type (e.g. **Plain Text**). **Important:** a description alone is not a readable Story Analysis source; attempting analysis without a source produces *This Story has no source file*. This is a documented UX/automation issue, not an analysis-service failure.
4. Supply metadata: synopsis, genres, themes, target audience, author. Language and other fields may also be available.
5. Save and select the Story; verify the Story ID, source type and metadata completeness.

The B.5.22 disposable Story:
- `STORY-001` — **The Quiet Console — CAP Persistence Acceptance**.
- Story source: Plain Text; author: **VSCS Acceptance Test**.
- 100% metadata completion has been observed.

### 3.2 Analyse Story

**Story → Story Definition → Analyse Story** (or **Story → Automation → Story Analysis** if routed to the same action).
1. Confirm Story source file exists and is readable.
2. Click **Analyse Story** once. A provider-backed call may incur cost.
3. The UI now shows **Story Analysis — Running**, an indeterminate progress dialog and elapsed seconds; this progress fix passed 2,405 automated tests and was observed in the real UI.
4. On completion, the **Story Analysis** review window shows source text, structured analysis, knowledge graph, validation & diagnostics. Buttons include **Reload Cached Analysis**, **Reload Cached Graph**, **Validate Story**, **Review AI Entities**, **Story Intelligence**, **Integration Acceptance**, and **Reanalyse Story**.
5. Review analysis and close the workspace. Verify the Story is **Analysed**. Approval cannot proceed from Draft/Imported solely because metadata is 100% complete.

**Observed B.5.22 analysis:** 1 story section, 7 sentence spans, 8 AI-proposed production entities, knowledge graph with 9 nodes. These are specific to the disposable Story, not general expectations.

**Cost caution:** Do not repeatedly click Analyse/Reanalyse while a previous provider call is running. **Reload Cached** actions should not trigger new provider generation.

### 3.3 Approve Story

After analysis and full metadata:
1. Confirm **Status: Analysed**, **Metadata: 100%**, **Ready to approve: Yes**.
2. Click **Approve**.
3. Confirm Story status becomes **Approved**. Locking is optional for the CAP Batch prerequisite; **Approved** and **Locked** are accepted source statuses in the existing batch service.

**B.5.22 observed:** `STORY-001` is **Approved**. Do not lock it just to advance the test.

### 4.5 False-failure avoidance checklist

Before reporting *missing planning/asset/CAP*:
- Is the correct disposable project open?
- Is Story source and analysis current?
- Is the Story approved?
- Were proposals merely generated, or reviewed/accepted and compiled?
- Does **Production Planning** list actual Episode, Scene and Shot records?
- Are Shot asset bindings actual records and what are their Draft/Ready statuses?
- Is the asset registered, category correct, and CAP specified?
- Is a cached CAP proposal legacy/current/stale/invalid?
- Is the operation explicitly offline, paid, Draft-only, reviewed, or production-authoritative?

Do not create artificial assets or promote Draft bindings just to satisfy a green UI check.

## 6. Assets, CAPs and the canonical workflow — UI verified through read-only acceptance

### 6.1 Asset discovery and context

**View → Canonical Profiles → Story → CAP Batch…** (available in the project's navigation):
1. Select Approved Story.
2. Click **Discover Shot Assets**. Discovery is Story-scoped to governed Shot bindings, not free-text mention of a prop.
3. Select an asset and click **Prepare CAP Context (Offline)**.
4. Check `approved_story_context` versus `unverified_shot`, source fields, fingerprints and warnings; Draft Shot bindings must remain unverified.
5. Click **Prepare Queue (Offline)** to inspect all discovered assets without provider calls, CAP writes or Canon approval.

### 6.2 Cache-first queue

- `cached_current`: context-bound cached proposal exists; **still unapproved**.
- `legacy_cached`: Story/asset/provider match, but governed Shot context was not fingerprinted at original generation; full review required.
- `missing`, `stale`, `invalid`, `context_blocked`, `already_specified`: different decisions/blockers, not synonyms for approved production readiness.

**Known operator example:** B5_19A had four missing CAPs and a legacy cached control-room proposal, but those are not B.5.22 current project assets. Never copy that status to the new project.

### 6.3 Reviewed Draft save

1. **Review Cached Proposal** first; only if necessary use **Generate / Regenerate Using AI (Paid)** with explicit provider/cost confirmation (one call per confirmation).
2. Review the specification. **Save Review & Continue** writes a working cached proposal; cancelling after it is **not** a zero-write cache test.
3. Review all required and populated attributes, selecting Accept/Edit/Reject/Defer deliberately.
4. The final **Save** rechecks Story, asset, provider and governed context fingerprints inside the existing service.
5. A successful reviewed save creates or updates a **Draft CAP only**. No Canon, MASTER image, asset approval or H3 permission is granted automatically.
6. Reopen the project and verify CAP Draft status, specification metadata and review provenance before describing this as end-to-end durable persistence.

Automated disk-backed acceptance B.5.22 passed **5 targeted tests and 2,403 full regression**. Actual desktop operator save/reopen remains pending.

## CAP Generation: persistent asset identity vs Shot events — development update (operator acceptance pending)

**Principle:** AI output is a reviewable proposal, not approved Canon. A high-quality provider should normally produce a usable Draft that requires operator verification, **not repeated manual rewriting**. Stable CAP fields must describe physical identity and repeatable across-Shot constraints. Temporal changes such as `the indicator pulses once and returns to steady` belong to the Shot narrative/Shot plan, not the permanent room's `architecture`, visual identity, Master Reference prompt or CAP continuity rules. An indicator's presence and fixed relation to the console may be described as a stable attribute if supported by approved Story evidence.

The OpenAI CAP pipeline now explicitly differentiates stable asset identity from Shot-specific events in fact extraction, Canon analysis and structured Draft generation. It instructs the model to preserve unambiguous ownership (e.g., a diagnostic console's blue display). This improves guidance but **cannot guarantee** that every model output is correct.

A conservative automated CAP identity-quality gate inspects the generated identity and continuity rules for obvious one-off indicator sequence wording. If detected, the pipeline automatically requests **at most one additional Draft generation** using the same source facts and corrective guidance; a second failure raises an error and never treats the faulty result as an approved specification. The optional extra request is potentially billable, and the existing paid-consent dialog discloses it. The worker remains under the shared Automation Progress window. No silent editing of evidence, CAP acceptance, reference generation or production approval is performed.

**Acceptance:** Pull the updated branch, run targeted tests in `tests/test_phase_20_19_3b5_1_openai_cap_schema.py`, full regression, Ruff check/format and Mypy; review the updated paid-consent wording. Test one disposable Engineering Control Room regeneration using Terra only after quality gates pass. Evaluate the produced architecture, continuity rules and master-reference prompt for stable asset identity and correct console/display ownership. Compare with the previous cached proposal, and retain manual review and Draft approval gates. Previously generated cached proposals are **not retroactively rewritten**.


## CAP source-grounding and relationship preservation — follow-up acceptance

**Purpose:** CAP generation must retain relationships explicitly supported by the approved Story, rather than inventing uncertainty or requiring repeated manual edits. In the disposable `The Quiet Console` project, the source says a diagnostic console stands beside a workstation, *its blue display glowing steadily*. The pronoun can grammatically refer to either object. The generator must not invent certainty about ownership; for explicitly possessive wording (e.g., *the diagnostic console's blue display*), it must also avoid inventing uncertainty. The later Terra Draft exposed this need for stronger source-grounding. This is a **source-grounding defect**, separate from the already-fixed one-time indicator pulse leaking into permanent identity.

**Pipeline correction:** The final structured CAP Draft stage now also receives the approved Story text as a **source-grounding cross-check**, while still using the earlier extracted and analysed facts as authority. The generation instructions forbid adding physical details merely because they appear plausible. A conservative source-relationship check flags the loss of an explicitly stated console/blue-display relationship when the Story uses unambiguous possession and the draft incorrectly declares ownership unspecified. Ambiguous pronouns do not trigger a forced ownership correction. It requests **at most one** corrective Draft pass using the same existing paid consent and Automation Progress infrastructure. If a flagged defect remains, generation fails closed, without caching the unusable new result or creating an approved CAP. Ambiguous text does not justify fabricating an attachment or location for the small indicator.

**Scope:** This is not a universal semantic entailment engine. The deterministic quality gate covers a demonstrated source-pattern failure; future generalisation should use evidence-linked relationship extraction and validation across asset categories. Human review remains required. Previously generated caches are not retroactively changed.

**Acceptance:** Run CAP schema targeted tests, Ruff lint/format, Mypy and complete regression. After all gates pass, discard the old preview (do not save it), restart VSCS, deliberately regenerate the Engineering Control Room with Terra (paid), then verify the output preserves the console's blue display, does not assert the indicator's unspecified mounting as an established fact, and keeps the one-off pulse out of permanent room identity and continuity. Do not mark a CAP Approved or asset Ready based only on model output.
