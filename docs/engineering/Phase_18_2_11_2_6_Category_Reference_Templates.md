# Phase 18.2.11.2.6 — Category Reference Templates

## Purpose

Define data-driven canonical reference coverage contracts per AssetCategory so VSCS can determine which production views are required, recommended or optional before the later readiness phase.

## Boundary

This phase answers **what reference coverage should exist** and **which required views are missing**. It does not decide whether the CAP is production-ready. Phase 18.2.11.2.7 consumes this coverage contract and applies readiness/lifecycle rules.

## Template contract

Every category template requires the externally authored ChatGPT MASTER. Derived reference views are classified as:

- **Required** — baseline production coverage expected for the category.
- **Recommended** — useful additional coverage that should be produced when practical.
- **Optional** — valid category-specific references that are not required for baseline coverage.

Views not listed by a category template are treated as not applicable by default rather than being presented indiscriminately in the generation UI.

## Baseline templates

- Character — MASTER, full body, left/right profile and face required; front/rear recommended.
- Ship — MASTER plus front, rear, port, starboard, top and bottom required; three-quarter/detail recommended.
- Vehicle — MASTER plus front, rear, left, right and top required.
- Prop — MASTER plus front, rear, left and right required.
- Location — MASTER and primary three-quarter required; aerial/detail recommended; interior/surface optional because location subtypes differ.
- Environment — MASTER and primary three-quarter required; aerial/surface recommended.
- Planet — MASTER, orbit and surface required.
- Uniform — MASTER, front, rear and both profiles required.
- Technology — MASTER plus front, rear, left and right required.
- Effect — MASTER required; variant recommended.
- Audio, Camera, Lighting, Reference and Other — MASTER only in the baseline contract.

The registry supports deliberate replacement of a category template so project-specific overrides can be introduced later without changing the coverage/generation services.

## Coverage semantics

Coverage compares the category template with the active production reference library.

Candidate, Approved and Locked references count as present for generation coverage. Rejected and Archived references do not. This prevents accidental duplicate generation while a Candidate awaits review, while allowing a rejected view to be regenerated.

Coverage publishes:

- present applicable views;
- missing required views;
- missing recommended views;
- present optional views;
- required-complete and recommended-complete convenience flags.

Lifecycle quality is intentionally not collapsed into coverage. A Candidate may be present for generation coverage but will not necessarily satisfy the readiness rules introduced in Phase 18.2.11.2.7.

## Generation integration

`DerivedReferenceGenerationService` exposes category coverage and `generate_missing_required()`.

The generation dialog now:

- shows the active Asset category;
- presents only views applicable to that category;
- labels each view Required, Recommended or Optional;
- marks existing active views as Present and disables duplicate selection;
- summarizes missing required/recommended coverage;
- exposes **Generate Missing Required Views**;
- continues to support manually selected applicable views.

MASTER is never generated by this action. If MASTER is missing, the operator is directed back to the governed ChatGPT MASTER attachment/revision workflow.

## Acceptance criteria

1. Every `AssetCategory` has a deterministic baseline reference template.
2. Every template requires exactly the externally governed MASTER as canonical authority.
3. Required/recommended/optional view sets are disjoint.
4. The registry supports future template replacement/override without UI hard-coding.
5. Coverage identifies present, missing required and missing recommended views from active library entries.
6. Rejected/Archived references do not satisfy coverage.
7. The generation UI displays category-aware requirement labels and hides non-applicable views.
8. Existing active views cannot be accidentally regenerated through the dialog.
9. `Generate Missing Required Views` generates only missing required derived views and never MASTER.
10. Overall production readiness remains deferred to Phase 18.2.11.2.7.
